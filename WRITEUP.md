# 2. Your pipeline (150 words)
The script starts from main, which sets up the input files, output paths and processing pipeline. It then starts the producer, which goes through the Parquet files and reads the video information from each row. For each video, decode_video opens the video using OpenCV and extracts frames at the required timestamps. These frames are grouped into packets and placed on a queue so that decoding and model processing can happen separately.The processing side takes these packets and passes them to process_group. It runs the object detection model on the sampled frames in batches and collects the predictions. The script then checks whether more frames need to be processed for seconds where the sampled frames disagree, instead of processing every frame from the start. Once the predictions for a video are ready, it combines them into the required per-second results, formats the output and writes an output line to the results file. This continues until all the videos have been processed.

# 3. Where the time goes (150 words)
The GPU processing seems to take the biggest part of the time in my final version. I tested decoding separately on Colab. The grab operation ran at around 1,266 to 1,613 frames/s, while a full read ran at around 922 to 1,036 frames/s. I also tested the GPU with different batch sizes. It went from 112 frames/s at batch size 8 to 125 at 16, 125 at 32 and 126 at 64. This showed that increasing the batch size helped initially, but there wasn't much improvement after 16. In the final run logs, each GPU was processing around 22 seconds of video per second. Based on these tests, GPU inference appears to be the main cost, but I would need a proper timing breakdown of the final pipeline to confirm this.

# 4. Checking correctness (100 words)
I compared my faster versions against reference CSVs generated by running the model on every frame. I started with 5 videos and then expanded the testing to 36 videos covering different objects like dogs, phones, laptops and cars. I also tested different sampling rates and checked how the F1 score changed. For fp16, I compared the predictions against the original and got 99.81% identical frames, with only 0.08% object flips across 36,602 frames. My final run also produced 1,650 videos with no missing gaps, duplicate entries or error lines. There are still some rare classes that need more testing.

# 5. Working with AI (100 words)
One suggestion from the AI that turned out to be wrong was its initial assumption that video decoding would be the main bottleneck. After I tested decoding separately, it seemed like decoding could become a problem, especially with limited CPU cores. But when I tested the GPU at different batch sizes, the results showed that GPU inference was actually the bigger concern. This changed how I approached the optimisation. Instead of spending more time trying to make decoding faster, I focused more on batching and GPU utilisation. It also showed me that I shouldn't just accept an AI suggestion without testing it against actual results.

# 6. Next steps (100 words)
If I had another week, I would first do a proper breakdown of the final pipeline to see exactly how much time is spent decoding, running inference and writing results. I would also test TensorRT or ONNX to see if they could improve inference speed, since I skipped them due to time constraints. Another thing would be expanding the correctness tests, especially for rare classes like dogs, which had very few true seconds in my test data. I would also test the adaptive controller on more real videos where it actually needs to increase sampling, and verify the timestamp handling against another decoder.
